## El problema no es comparar archivos; es decidir qué puede salir del proceso

Comparar dos archivos parece sencillo hasta que el contenido incluye tokens, contraseñas, URLs internas o configuraciones que no deberían aparecer en un registro de CI. Un diff tradicional es excelente para explicar exactamente qué cambió. También puede ser una forma bastante eficiente de publicar un secreto por accidente.

[Resource Contract Checks](https://github.com/YagoLagrottiBracco/resource-contract-checks) aborda una versión acotada de ese problema: comparar la estructura de dos documentos JSON y comprobar si un archivo .env candidato conserva el conjunto esperado de claves. El mismo motor alimenta una CLI local y una GitHub Composite Action. La diferencia entre ambas interfaces no es cosmética: cada una tiene una política de salida adecuada a su contexto de ejecución.

La herramienta no sustituye a JSON Schema, la validación de dominio ni un gestor de secretos. Comprueba contratos sencillos entre archivos. Ese límite importa: una herramienta pequeña y predecible suele ser más fácil de auditar que un validador que intenta interpretar cualquier formato de configuración.

## Dos contratos distintos requieren comprobaciones distintas

En el modo JSON, el contrato es estructural y también compara los valores. El motor analiza ambos documentos, recorre objetos y arrays de forma recursiva y registra rutas añadidas, eliminadas o modificadas. El orden de las propiedades de los objetos no importa; la posición de los elementos de los arrays sí.

En el modo .env, la pregunta es diferente. El objetivo es determinar si el candidato declara las mismas claves que la referencia, no comparar sus valores. Así se puede comprobar la forma del entorno sin imprimir DATABASE_URL, API_KEY ni ningún otro contenido.

Esta distinción evita un error habitual: llamar a todo “validación de configuración” y asumir que una única política de salida sirve para formatos con riesgos diferentes.

## JSON: diferencias estructurales, límites explícitos y precisión numérica

El comparador no realiza una comparación textual línea por línea. Primero analiza ambos documentos con JSON.parse. Después recorre la estructura y construye rutas JSON Pointer, escapando la tilde como ~0 y la barra como ~1.

Un cambio puede representarse así:

~~~json
{
  "path": "/services/0/timeout",
  "kind": "changed",
  "before": 10,
  "after": 15
}
~~~

Esta representación apunta a un campo, no a una línea física. Reformatear el JSON o cambiar el orden de las propiedades de un objeto no crea una diferencia artificial.

Hay límites deliberados:

- cada entrada está limitada a 200.000 bytes UTF-8 en la capa de lectura;
- se rechazan estructuras con más de 100 niveles de profundidad;
- el informe almacena como máximo 500 cambios y marca truncated cuando supera ese límite;
- el JSON inválido, una entrada demasiado grande y los números que perderían precisión se tratan como entrada inválida.

El último punto merece atención. JavaScript representa los números JSON mediante Number, que utiliza coma flotante de doble precisión. Los enteros fuera del rango seguro y los decimales cuya representación cambiaría durante la conversión no deberían compararse silenciosamente como si fueran exactos. El motor examina los lexemas numéricos originales y rechaza los casos en los que la conversión no conservaría el valor.

Es una decisión conservadora. Otra implementación podría utilizar una biblioteca decimal o un parser de números de precisión arbitraria, pero añadiría complejidad y una dependencia al camino crítico. Para archivos de contrato pequeños, fallar explícitamente es mejor que declarar igualdad basándose en un número redondeado.

El comparador tampoco es un validador de esquemas. No recibe una especificación de tipos, rangos o campos obligatorios. Responde si dos documentos concretos son estructuralmente iguales y, cuando no lo son, dónde difieren. Si el requisito es validar un payload contra un contrato versionado, JSON Schema u otro lenguaje de esquemas es más apropiado.

## .env: comparar claves sin devolver valores

El parser de .env es intencionalmente más pequeño que un intérprete de shell. Ignora líneas vacías y comentarios, acepta asignaciones con el formato NOMBRE=valor y también el prefijo export, y extrae únicamente nombres que cumplen un patrón de identificadores.

~~~text
DATABASE_URL=
API_KEY=
PORT=3000
~~~

La comparación produce cuatro grupos relevantes: claves ausentes, claves adicionales, duplicados y líneas inválidas. Los valores no forman parte del resultado. Si API_KEY existe en ambos archivos, la herramienta no intenta determinar si los valores son iguales, válidos o están autorizados.

Esa decisión reduce la exposición de datos, pero también define el límite funcional: el modo .env no evalúa interpolación de variables, expresiones de shell, valores multilínea ni la semántica de cada configuración. No ejecuta el archivo y no debe tratarse como un parser completo de todos los dialectos de dotenv.

Los duplicados y las líneas sin una asignación válida producen el estado invalid. Las claves ausentes o adicionales producen different. Por tanto, un archivo puede reconocerse como archivo de entorno y aun así incumplir el contrato esperado.

## La CLI controla la entrada antes de llamar al motor

La CLI se construyó con APIs nativas de Node.js y no instala dependencias. Acepta rutas de archivos regulares o un guion para leer una única entrada desde stdin. También exige UTF-8 válido, limita cada entrada a 200.000 bytes y rechaza otros tipos de archivo.

Hay un detalle operativo que vale la pena conservar: los archivos se abren con O_NONBLOCK antes de comprobar su tipo. Así se evita quedar bloqueado indefinidamente ante un FIFO, por ejemplo, antes de poder rechazarlo mediante fstat. El tamaño se comprueba antes de leer y nuevamente durante la lectura, porque un archivo puede crecer después de stat.

Uso local:

~~~sh
resource-tools json before.json after.json --json
resource-tools env .env.example .env.ci
cat candidate.json | resource-tools json reference.json -
~~~

Los códigos de salida son estables y sencillos:

| Código | Significado |
| ---: | --- |
| 0 | los documentos son iguales o el contrato es válido |
| 1 | se encontraron diferencias |
| 2 | uso inválido o entrada inválida |

La salida de la CLI es más detallada que la de la Action. En modo .env puede mostrar nombres de claves y números de línea, pero no valores. En modo JSON, el informe puede incluir los valores before y after. Por eso, la salida JSON no debe enviarse a ciegas a un registro público cuando los documentos pueden contener credenciales o datos privados.

## La GitHub Action tiene una frontera de salida más estricta

La Composite Action recibe tool, reference y candidate. En lugar de interpolar esos argumentos directamente en un comando de shell, action.yml los pasa mediante variables de entorno. Un script fijo ejecuta Node.js usando la ruta del propio paquete de la Action.

El runner utiliza la misma función evaluate() que la CLI, pero no imprime el objeto de diferencias. El resumen de GitHub Actions contiene únicamente estado y recuentos: cuántas claves faltan o sobran, cuántos duplicados o líneas inválidas se encontraron, o cuántas diferencias JSON se detectaron. No publica rutas, nombres de claves, fragmentos ni valores.

~~~yaml
steps:
  - uses: actions/checkout@v4
  - uses: YagoLagrottiBracco/resource-contract-checks@44b484f7eba8e5b074713eb753e2ae18db434aa6
    with:
      tool: env
      reference: .env.example
      candidate: .env.ci
~~~

La Action expone status y exit-code. El estado puede ser equal, different o invalid; los códigos siguen siendo 0, 1 y 2. El paso falla cuando encuentra diferencias o una entrada inválida, por lo que puede actuar como gate de CI sin convertir el resumen en un diff de secretos.

Esto no significa que el contenido nunca exista en la memoria del runner. El proceso necesita leer los archivos para compararlos. La garantía es más concreta: la Action no los envía por la red ni los incluye deliberadamente en los registros o en el resumen. Un runner comprometido, una dependencia maliciosa u otro paso con acceso al workspace siguen dentro del modelo de amenazas. La herramienta reduce las filtraciones accidentales; no es una bóveda ni un sandbox.

También es importante no generalizar la política de la Action a la CLI. El informe JSON de la CLI puede revelar valores. La Action, por diseño, publica solamente recuentos y estado. Esa diferencia está documentada y cubierta por pruebas.

## Pruebas que verifican lo que no debe aparecer

Las pruebas de la Action crean archivos temporales con valores ficticios que parecen secretos y verifican que no aparezcan en GITHUB_STEP_SUMMARY, stdout ni stderr. Otro caso envía argumentos con apariencia de comandos de shell y Markdown malicioso, y confirma que no se interpolan en comandos ni se reproducen en el resumen. También hay una prueba específica para diferencias JSON: el informe debe contar el cambio sin imprimir el valor privado ni el nombre de la clave.

El workflow del repositorio ejecuta la suite en Node.js 20 y 22 y también invoca la Action dentro de su propio repositorio con archivos .env sintéticos. Las dos ejecuciones registradas el 17/10/2026 terminaron correctamente. Esto demuestra la ejecución automatizada en esas versiones del runtime; no es una medición de rendimiento en producción ni una garantía sobre todos los runners posibles.

El motor también está limitado por tamaño de entrada, profundidad de anidamiento y cantidad de diferencias informadas para mantener el trabajo predecible. Esos límites no sustituyen el aislamiento del runner ni el rate limiting, pero reducen la posibilidad de que una entrada accidentalmente enorme consuma recursos sin control.

## Distribución: la CLI y la Action son publicaciones distintas

El motor JavaScript distribuido se genera a partir de la implementación TypeScript utilizada en el portafolio. La compilación empaqueta el mismo núcleo para la CLI y la Action, evitando mantener dos implementaciones independientes de la comparación.

La Action está publicada en su repositorio dedicado con las etiquetas v1 y v1.0.0, además de la release v1.0.0. El README recomienda fijar un SHA completo revisado en workflows que necesiten más reproducibilidad que una etiqueta móvil. La ejecución de la release pasó en Node.js 20 y 22.

La CLI se distribuye mediante un archivo TGZ versionado alojado en el portafolio. El paquete del registro npm todavía no se ha publicado; una URL de archivo instalable no equivale a una publicación en npm. Tampoco se afirma que la lista del GitHub Marketplace esté completada. Son canales de distribución distintos, cada uno con su propio paso de publicación.

Para adoptar la Action, revisa el código y fija su SHA. Para usar la CLI, instala el TGZ versionado y ejecuta resource-tools --help. La herramienta requiere Node.js 20 o superior y no realiza solicitudes de red durante la comprobación.

## Para qué no usaría esta herramienta

No utilizaría el modo .env para validar si una URL, un token o una contraseña tienen el formato correcto. Comprueba la presencia de claves, no la semántica de sus valores. Tampoco usaría la comparación JSON como sustituto de JSON Schema, pruebas de compatibilidad de API o validación de reglas de negocio.

No publicaría el resultado JSON detallado en registros accesibles a terceros sin comprobar antes si los valores pueden contener datos sensibles. Y no trataría la salida resumida de la Action como prueba de que el runner es seguro: es una política de logging, no una frontera de aislamiento.

La utilidad del proyecto está precisamente en su alcance reducido: una comparación local, determinista y acotada, con una interfaz de CI que expone solo lo necesario para decidir si el contrato pasó.

## Lista de comprobación para adoptar validaciones de contrato en CI

1. Decide si el contrato compara valores o solamente la forma de las claves.
2. Establece límites de tamaño, profundidad y volumen del informe.
3. Distingue igualdad, diferencias y entrada inválida con códigos de salida estables.
4. Separa el resultado interno de la política de logging de la integración.
5. Comprueba explícitamente que los valores sensibles no aparecen en stdout, stderr ni en el resumen.
6. Pasa entradas no confiables mediante variables de entorno o argumentos estructurados, no mediante interpolación de shell.
7. Fija Actions externas por SHA cuando importe la reproducibilidad de la cadena de suministro.
8. Documenta lo que la herramienta no valida, para que un diff estructural no se confunda con una validación de esquema.

El punto central no es ocultar todas las diferencias. Es decidir qué información hay que calcular, qué se puede mostrar y qué debe permanecer dentro del proceso. Un buen verificador de contratos hace explícita esa frontera.
