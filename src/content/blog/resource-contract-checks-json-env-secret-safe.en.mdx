## The problem is not comparing files; it is deciding what may leave the process

Comparing two files looks simple until they contain tokens, passwords, internal URLs, or configuration that should never appear in a CI log. A conventional diff is excellent at explaining exactly what changed. It can also be an efficient way to publish a secret by accident.

[Resource Contract Checks](https://github.com/YagoLagrottiBracco/resource-contract-checks) addresses a narrow version of that problem: compare the structure of two JSON documents and check whether a candidate .env file preserves the expected set of keys. The same engine powers a local CLI and a GitHub Composite Action. The difference between those interfaces is not cosmetic; each has an output policy suited to its execution context.

The tool is not a replacement for JSON Schema, domain validation, or a secrets manager. It checks simple file contracts. That boundary matters: a small, predictable tool is usually easier to audit than a validator that tries to interpret every configuration format.

## Two different contracts require two different checks

In JSON mode, the contract is structural and includes value comparison. The engine parses both documents, walks objects and arrays recursively, and records added, removed, or changed paths. Object property order does not matter; array position does.

In .env mode, the question is different. The goal is to determine whether the candidate declares the same keys as the reference, not to compare their values. This makes it possible to check the shape of an environment without printing DATABASE_URL, API_KEY, or any other content.

That distinction avoids a common mistake: calling everything “configuration validation” and assuming one output policy is appropriate for formats with different risks.

## JSON: structural differences, explicit limits, and numeric precision

The comparator does not perform a line-by-line text comparison. It first parses both documents with JSON.parse. It then walks the structure and builds JSON Pointer paths, escaping tilde as ~0 and slash as ~1.

A change can be represented like this:

~~~json
{
  "path": "/services/0/timeout",
  "kind": "changed",
  "before": 10,
  "after": 15
}
~~~

This representation points to a field rather than a physical line. Reformatting JSON or changing the order of an object's properties does not create an artificial difference.

There are deliberate limits:

- each input is limited to 200,000 UTF-8 bytes at the reading layer;
- structures deeper than 100 levels are rejected;
- the report stores at most 500 changes and marks truncated when that ceiling is exceeded;
- invalid JSON, oversized input, and numbers that would lose precision are treated as invalid input.

The last point deserves attention. JavaScript represents JSON numbers with Number, which uses double-precision floating point. Integers outside the safe range and decimals whose representation would change during conversion should not be silently compared as if they were exact. The engine examines the original numeric lexemes and rejects cases where conversion would not preserve the value.

This is a conservative choice. Another implementation could use a decimal library or an arbitrary-precision number parser, but that would add complexity and a dependency to the critical path. For small contract files, failing explicitly is better than reporting equality based on a rounded number.

The comparator is not a schema validator either. It does not receive a specification of types, ranges, or required fields. It answers whether two concrete documents are structurally equal and, when they are not, where they differ. If the requirement is to validate a payload against a versioned contract, JSON Schema or another schema language is a better fit.

## .env: compare keys without returning values

The .env parser is intentionally smaller than a shell interpreter. It ignores blank lines and comments, accepts assignments in the form NAME=value and the export prefix, and extracts only names that match an identifier pattern.

~~~text
DATABASE_URL=
API_KEY=
PORT=3000
~~~

The comparison produces four relevant groups: missing keys, extra keys, duplicates, and invalid lines. Values are not part of the result. If API_KEY exists in both files, the tool does not try to determine whether the values are equal, valid, or authorized.

That decision reduces data exposure, but it also defines the functional boundary: .env mode does not evaluate variable interpolation, shell expressions, multiline values, or the semantics of each setting. It does not execute the file and should not be treated as a complete parser for every dotenv dialect.

Duplicates and lines without a valid assignment produce the invalid state. Missing or extra keys produce different. A file can therefore be recognizable as an environment file and still fail the expected contract.

## The CLI controls input before calling the engine

The CLI uses native Node.js APIs and installs no dependencies. It accepts regular file paths or a hyphen to read one input from stdin. It also requires valid UTF-8, limits each input to 200,000 bytes, and rejects other file types.

There is an operational detail worth keeping: files are opened with O_NONBLOCK before their type is checked. This avoids blocking indefinitely on a FIFO, for example, before the program can reject it with fstat. Size is checked before reading and again while reading, because a file can grow after stat.

Local usage:

~~~sh
resource-tools json before.json after.json --json
resource-tools env .env.example .env.ci
cat candidate.json | resource-tools json reference.json -
~~~

Exit codes are stable and simple:

| Code | Meaning |
| ---: | --- |
| 0 | documents are equal or the contract is valid |
| 1 | differences were found |
| 2 | invalid usage or invalid input |

The CLI output is more detailed than the Action output. In .env mode it can show key names and line numbers, but not values. In JSON mode, the report may include before and after values. Therefore, the JSON output option should not be sent blindly to a public log when documents may contain credentials or private data.

## The GitHub Action has a stricter output boundary

The Composite Action receives tool, reference, and candidate. Instead of interpolating those arguments directly into a shell command, action.yml passes them through environment variables. A fixed script runs Node.js using the action's own package path.

The runner uses the same evaluate() function as the CLI, but it does not print the difference object. The GitHub Actions summary contains only status and counts: how many keys are missing or extra, how many duplicates or invalid lines were found, or how many JSON differences were detected. It does not publish paths, key names, snippets, or values.

To keep the example readable on narrow screens, only the `with` block is shown below; the `uses` reference should point to a reviewed Action commit rather than a moving tag.

~~~yaml
with:
  tool: env
  reference: .env.example
  candidate: .env.ci
~~~

The Action exposes status and exit-code. The status can be equal, different, or invalid; the exit codes remain 0, 1, and 2. The step fails when it finds differences or invalid input, so it can act as a CI gate without turning the summary into a secret diff.

This does not mean the content never exists in runner memory. The process must read the files to compare them. The guarantee is narrower: the Action does not send them over the network and does not deliberately include them in logs or the summary. A compromised runner, a malicious dependency, or another step with workspace access remains inside the threat model. The tool reduces accidental disclosure; it is not a vault or a sandbox.

It is also important not to generalize the Action's policy to the CLI. The CLI's JSON report can reveal values. The Action deliberately publishes only counts and status. That difference is documented and tested.

## Tests that verify what must not appear

The Action tests create temporary files with fake values that look like secrets and verify that they do not appear in GITHUB_STEP_SUMMARY, stdout, or stderr. Another case supplies shell-command-like arguments and malicious Markdown, confirming that they are neither interpolated into commands nor reproduced in the summary. A dedicated JSON test checks that the report counts a change without printing the private value or key name.

The repository workflow runs the suite on Node.js 20 and 22 and also invokes the Action inside its own repository with synthetic .env files. Both recorded runs on 17 October 2026 completed successfully. This proves automated execution on those runtime versions; it is not a production performance benchmark or a guarantee about every possible runner.

The engine is also bounded by input size, nesting depth, and number of reported differences to keep work predictable. Those limits do not replace runner isolation or rate limiting, but they reduce the chance that an accidentally huge input consumes unbounded resources.

## Distribution: the CLI and the Action are separate releases

The distributed JavaScript engine is generated from the TypeScript implementation used in the portfolio. The build packages the same core for the CLI and the Action, avoiding two independent implementations of the comparison logic.

The Action is published in its dedicated repository with v1 and v1.0.0 tags and a v1.0.0 release. The README recommends pinning a reviewed full SHA in workflows that need stronger reproducibility than a movable tag. The release workflow passed on Node.js 20 and 22.

The CLI is distributed through a versioned TGZ hosted by the portfolio. The npm registry package has not been published; an installable archive URL is not the same thing as an npm publication. A GitHub Marketplace listing is also not claimed as complete. These are separate distribution channels, each with its own publication step.

To adopt the Action, review the code and pin its SHA. To use the CLI, install the versioned TGZ and run resource-tools --help. The tool requires Node.js 20 or newer and makes no network requests during a check.

## What I would not use this tool for

I would not use .env mode to validate whether a URL, token, or password has the right format. It checks key presence, not value semantics. I would not use JSON comparison as a replacement for JSON Schema, API compatibility testing, or business-rule validation either.

I would not publish the detailed JSON result to logs accessible to third parties without first checking whether the values may contain sensitive data. And I would not treat the Action's summarized output as proof that the runner is secure: it is a logging policy, not an isolation boundary.

The project's usefulness comes from its narrow scope: a local, deterministic, bounded comparison, with a CI interface that exposes only what is needed to decide whether the contract passed.

## Checklist for adopting contract checks in CI

1. Decide whether the contract compares values or only the shape of keys.
2. Set limits for input size, nesting depth, and report volume.
3. Distinguish equality, differences, and invalid input with stable exit codes.
4. Separate the internal result from the integration's logging policy.
5. Explicitly test that sensitive values do not appear in stdout, stderr, or the summary.
6. Pass untrusted inputs through environment variables or structured arguments, not shell interpolation.
7. Pin external Actions by SHA when supply-chain reproducibility matters.
8. Document what the tool does not validate, so a structural diff is not mistaken for schema validation.

The central point is not to hide every difference. It is to decide what information must be computed, what may be displayed, and what should remain inside the process. A good contract checker makes that boundary explicit.
